## 新失败：嵌套迭代器清理被单个 Dispose 异常截断

归档入口 [v003_r3_checks.cs](../../tools/verification/v003_r3_checks.cs)，`V003R3Checks.Run`，只通过公开 NativeSuperSpell/History/TaskHost 接口检查。没有改变原两卡配置、等待时长、FSM或业务代码。

最小复现使用真实 EX1_134 根、NativeSuperSpellTaskHost、NativePowerExecution。有效规范化 Tasks 为 `HistTagChange/type4/tag49/entity20 → HistMetaData/type8/metaType0/metaData0 → HistTagChange/type4/tag44/entity20`，两级映射 visual0 → target7 → metadata1。Entity/Zone/loading/处理器等服务明确绑定；CanDoTask=false，真实执行器 WaitingRequests=1，未完成的前置任务使 Until 真实进入等待。

History 适配器把真实 Until 迭代器套入三层可 Dispose 的 IEnumerator。外两层通过 Current 返回内层；叶层委托真实 Until。每层都已执行 MoveNext，调度器按 `stack.Push(nested)` 接管各层，正常场景及相同暂停状态下无故障 Cancel/Dispose 均验证每层恰好 Dispose 一次。外层 Dispose 不递归处置子层，避免和已经接管子层的调度器重复释放；这一规则与该调度器现有栈模型一致，不是未交付给宿主的对象。

配置叶层 Dispose 在完成真实 Until.Dispose 后抛出同一个受控 `IOException`，再从根分别调用 Cancel 或 Dispose，实际异常发生在这次根停止调用内。期望：真实故障可诊断，其余已接管迭代器继续清理，或者保留明确可重试的剩余清理。实际：

定位：`NativePresentationCoroutines.cs:58` 的 Close 先设 job.Done=true，再在61行直接循环 Pop/Dispose；首个 Dispose 抛出后，剩余栈与 `job.wait=null` 未执行。74行 Dispose 提前设置 disposed=true，遍历被异常打断，jobs.Clear 未执行。根 `NativeSuperSpell.cs:292` 捕获并保留原 IOException，仍停止真实 TaskHost，但重复 Cancel 不再进入首次清理块；重复 Dispose 也无法重开该时钟。根 Until 的 finally（144行）因此未运行，metadataPending仍1。反射只用于这一诊断输出，不作为构造状态或判定通过的依据。

影响与边界：已观察的是支持的显式 History 适配器所交付迭代器的清理丢失，以及根内部票据未归还。LastError 为原 IOException 对象，**没有吞异常**；Host.WaitingRequests=0、没有虚构 Completed/Finished。这个暂停的刺骨案例尚未创建原克隆，**没有已观察的原图/RT泄漏**；公开 Pending=0是取消getter的表现，不能证明内部finally已运行。普通深层停止、真实原图回收和回收失败显式重试另有通过证据。该反例不声称纯 Dictionary 的 TaskHost 自身会产生此异常，不声称正式无历史 UI 会自发进入此分支，也不是原raw历史传输。

这是本 Task 已支持的嵌套 History、停止、Dispose和故障清理合同内的失败。若适配器外层在finally持有资源，本轮证据只证明它的清理未被调用，不把潜在资源后果升级为已经观察的泄漏。探针finally在观察后手动关闭未收到Dispose的fixture迭代器，不通过此补救制造产品成功。
