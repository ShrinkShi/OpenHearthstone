## F1 / P2：取消后的晚到 None 回收异常没有诊断

Observed：两个全新 Unity 进程均以退出码 1 复现。独立探针为 [v002_r1_late_none.cs](../../tools/verification/v002_r1_late_none.cs)，不依赖既有检查器的 Probe、Scheduler 或断言。

最小输入/调用顺序：

1. 有效 Root/Source/Target、明确无 metadata 映射（`-1`）、零秒 spawn delay。调度器按契约立即推进至首个 yield，返回可等待句柄。
2. `Spawn(0)` 后恢复一次，获得独立克隆，并登记 finished/state-started 回调；`Pending=1`、`ActiveClones=1`。
3. `CancelAll()`：第一次 `Release(false)` 抛 `release-attempt-1`。此时取消和该次回收错误均经 Error 通知，克隆保留供重试。
4. 将克隆状态置为 None，调用原先登记的 state-started 回调。第二次 `Release(false)` 抛新的 `release-attempt-2`。

期望：第二次错误也通过 Error/LastError 可观察，保持取消计数、完成及回收幂等。实际：

```text
V002_LATE_NONE attempts=2 errorsBefore=2 errorsAfter=2
lastError=OperationCanceledException lastMessage=The operation was canceled.
retained=1 diagnosticDelivered=False
V002_REPORTED_ERRORS release:release-attempt-1 | cancel:The operation was canceled.
V002_EXPLICIT_RETRY recovered=True attempts=3 pending=0 cancelled=1 finishes=0
```

根因定位：`NativeSuperImpact.cs:239` 的 None 回收 catch 调用 `Fail(request,"release",error)`；`:185` 对已经 stopped 的请求直接返回，因此既不 Report，也不更新 LastError。`NativeSuperArea.cs:48` 登记的状态回调在取消后仍能调用此路径。不同于 `Routine.MoveNext` 的 stopped 分支和 `CancelAll` 的显式重试分支，二者已有 Report 保护。

影响限定：重试时出现的新回收错误会静默丢失，宿主不能从诊断获知该次失败。克隆仍保留，第三次显式 CancelAll 可以成功释放；本轮没有据此声称永久泄漏或 pending 重复扣减。两个新进程均从新建 fixture 开始，并在 finally 清理。

- 首次：PID 16952，`work/v002-r1-late-none.log:284`，退出 1。
- 再次：PID 11440，`work/v002-r1-late-none-repeat.log:259`，退出 1。
- 失败标准：Task 验收标准 2（异常/取消/释放边界），以及目标“失败可诊断”；专题明确要求取消后的回收异常仍经 Error/LastError 上报。
- 解除条件：修复已停止请求在晚到 None 路径上的回收错误诊断，增加该序列回归；不得重复扣 pending、重复完成或重入 Release，保留失败克隆供显式重试。功能修复后由全新 Verification 回合验证，不能以本报告中的正常检查代替。
